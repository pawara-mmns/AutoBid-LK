# Architecture decisions

## 2026-10-11 — Stage 5 seller management

1. **Separate private intake from approved discovery.** Public listings have no owner or reserve/contact information. Private seller submissions avoid widening public grants/DTOs or inventing publication. Only draft and pending review are supported; review decisions arrive in the next authorized phase.
2. **Controlled operations.** Customers SELECT owned rows and invoke narrow SQL RPCs without direct table writes. Fixed search paths, `auth.uid()` ownership, parent locks, revisions, bounded fields, quotas and SQL final validation protect direct API callers as well as the UI. Repeated creation/submission is idempotent; no elevated key is configured.
3. **Recoverable partial drafts.** Persist incomplete details/last step after 800ms, serialize saves, drain newer edits before navigation/submission and surface conflicts. Retry keeps current values. No private data goes into browser storage. Guests sign in before entering details.
4. **Canonical exact prices.** Reuse BigInt-based LKR helpers, store bounded integer cents, keep minimum private and validate minimum <= expected <= optional Buy Now. Durations 1/3/7 (default 3) are preferences only.
5. **Untrusted private media.** Owner Storage access cannot itself certify pixels. Byte decoding/re-encoding, immutable paths, quotas, private preview authorization and final checks prevent unsafe/public rendering through the app. Future publication must validate again. Sharp is an explicit pinned dependency because MIME/header checks cannot decode/optimize photos. Sources: [Supabase private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage RLS](https://supabase.com/docs/guides/storage/security/access-control), [Sharp input limits](https://sharp.pixelplumbing.com/api-constructor/).
6. **Honest commitments.** Submission records self-declared ownership/accuracy and a versioned intake agreement. Typed phones stay unverified. Fees/auction commitments require future approval and agreement before publication. Existing validated account email is reused.
7. **Verification isolation.** Seller browser checks persist drafts and execute Storage policies in actual PostgreSQL with synthetic Auth/object APIs. This remains test-only. Real provider lifecycle/Storage/SMTP, reviewed translations, device-camera and deployment limits remain acceptance gates. Stop after Stage 5.

## 2026-10-09 — Phase 0

1. **Feature-based modular monolith.** Next.js owns routing/rendering; domain services/schemas will live in feature modules. Add folders when used so the foundation does not imply absent features exist.
2. **npm with exact direct versions and a lockfile.** Stable registry releases are selected; Next.js and eslint-config-next match at 16.4.0, React/React DOM at 19.3.0. TypeScript 5.9.3 is a conservative compatible compiler rather than adopting a new major solely for recency. Node 24 is the local/default runtime.
3. **Tailwind 4 CSS-first configuration.** Use the official PostCSS integration; semantic CSS variables are the design token source. ESLint uses a flat config and the standalone CLI because Next.js 16 build does not run lint.
4. **Source-owned shadcn/ui Radix Button.** Use Slot composition, CVA variants and class merging; keep only the currently needed variants. Adapt to touch sizing and translated-label wrapping. No component gallery, theme switcher or unused primitives.
5. **Server rendering and system fonts.** The static foundation does not need a client application or external image/font dependencies. Future features introduce interactivity where needed; no premature React Compiler configuration.
6. **English now, structured localization immediately.** Centralize copy and metadata; reserve en/si/ta and distinguish supported from available languages. No inert language picker or simulated translations. Full localization/routing arrives in Phase 7.
7. **Configuration without credentials.** Allowlist/validate the optional public site origin with Zod and sanitize failures. Phase 0 starts without env files. Supabase clients/dependencies/schema and generated types arrive in Phase 1; no elevated keys are configured.
8. **Money uses integer minor units.** Future LKR records use cents (100 cents per rupee) with PostgreSQL bigint and precision-safe boundaries. Choose representation/conversion during the database phase before writing any financial code. No money calculations exist yet.
9. **Honest pre-launch shell.** In-page links explain the planned experience. No fake auctions/stats/verification claims, account controls, subscription form or placeholder workflows. Search engines receive noindex until release readiness.
10. **Verification tooling established early.** Vitest checks environment failure/sanitization/allowlisting. Playwright checks the production shell on desktop/mobile plus keyboard and 404 recovery. Further domain tests must verify real security/behavior rather than mirror implementation.
11. **Compatible lint tooling despite upstream maintenance limitations.** ESLint 9.39.5 satisfies the React/import/accessibility plugins bundled with eslint-config-next; ESLint 10 currently conflicts with their peer ranges. npm marks ESLint 9 deprecated. The lint-only `braces` dependency has an unpatched nested-pattern denial-of-service advisory (GHSA-vfj7-8cjw-p6xm), reported across five transitive packages. Do not force a framework downgrade or hide the finding with an unverified override. Reassess upstream releases in Phase 1; production dependencies are unaffected according to npm audit.
12. **Stable project instructions.** Next.js 16.4 automatically appends framework agent rules on development startup. Set its documented `agentRules` option to false so the manually maintained AGENTS.md remains the source of project rules. Version-matched Next.js documentation also ships under node_modules/next/dist/docs/.

## 2026-10-09 — Phase 1

1. Official @supabase/ssr browser/server clients and Next.js Proxy manage cookie sessions. Proxy uses getClaims; server guards/actions independently use getUser for provider validation. The static public homepage stays outside session checks.
2. One profile per Auth user; buying and selling share the same account. Optional dealer_profiles hold protected verification state. Separate admin_grants are writable only by separately authorized trusted provisioning; roles are never inferred from editable metadata.
3. RLS is combined with column grants. Customers can read only their own private rows, edit safe profile fields and request pending dealer status. An admin grant currently grants entry access, not blanket profile visibility or moderation tools.
4. Email confirmation and password recovery support both PKCE codes and token hashes. Origin comes from trusted configuration; destinations/token types are allowlisted. Email templates are language-specific provider assets. Error feedback never exposes provider internals or secrets.
5. PGlite is a development-only PostgreSQL test/type-generation dependency. It makes actual SQL/RLS verification reproducible without Docker or credentials. Its Auth fixture is synthetic and does not replace real Supabase Auth, PostgREST or SMTP acceptance tests.
6. E2E builds explicitly without Supabase settings on port 3100, preserving an existing server on 3000 and avoiding accidental project calls. A normal build restores environment configuration afterward.

Sources: [Supabase SSR clients](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [password auth](https://supabase.com/docs/guides/auth/passwords), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [CLI configuration](https://supabase.com/docs/guides/local-development/cli/config) and [PGlite](https://pglite.dev/docs/).

## 2026-10-09 — Phase 2

1. **Minimum public read model.** No vehicle tables existed in migrations or the checked exposed project schema. Use vehicle_listings and vehicle_media without duplicating private profiles or creating speculative seller/auction tables. A future owned workflow must publish a safe projection after separately authorized review.
2. **Anonymous server reads with two visibility boundaries.** Reuse validated public Supabase configuration in a cookie-free server-only client. Explicit projections and approval/publication checks supplement RLS/column grants. An authenticated visitor cannot accidentally widen public data through their session.
3. **Shareable bounded discovery.** GET forms use one validated URL schema, escaped LIKE operands, fixed SQL sort columns, deterministic ID tie-breakers and 12-card pagination. Bounded invoker facets avoid downloading the catalog to populate filters. Money is exact integer cents end to end.
4. **Private approved-photo delivery.** Private Storage and parent/media RLS control raw reads; a local UUID route checks raster path/MIME/size before Next Image optimization. Optimized public bytes can survive revocation in caches; document that limit and require a purge policy before release rather than implying immediate recall.
5. **404 before streaming.** Resolve detail visibility in its layout before the child loading boundary can flush HTTP 200. Share the request-local cached lookup with the page/metadata. Browse retains its own Suspense skeletons.
6. **Existing tooling, isolated public fixtures.** A loopback test-only REST/Storage adapter executes the real migration SQL as anon in PGlite. It tests real SDK queries and browser behavior without populating production or claiming provider integration. E2E builds unconfigured and fixture modes, closes resources and restores normal configuration. No new Phase 2 dependency/framework was needed.
7. **Honest pre-release information.** Functioning footer/selling routes explain current availability. Other categories, selling and bidding are clearly unavailable. Display approval is not an inspection badge. English dictionaries and existing semantic tokens remain the only active language/design system.

References: [Supabase pagination](https://supabase.com/docs/reference/javascript/range), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [Next Image cache behavior](https://nextjs.org/docs/app/api-reference/components/image) and [Next notFound/streaming behavior](https://nextjs.org/docs/app/api-reference/file-conventions/not-found).

## 2026-10-10 — Extension-injected body attributes

Use suppressHydrationWarning only on the root body for the observed extension-generated `__processed_…` attribute. The body has no application-controlled dynamic attributes, so this small compatibility boundary preserves SSR and child diagnostics while avoiding the reported warning. It is an escape hatch, not removal of injected markup or a blanket fix for extensions that modify nested elements. A document-start injection test verifies the exact marker and working interactions in development and production. Developer tests may explicitly reuse localhost:3000; production tests retain their isolated port-3100 server. [React documents the one-level suppression boundary](https://react.dev/reference/react-dom/client/hydrateRoot#suppressing-unavoidable-hydration-mismatch-errors).

## 2026-10-11 — UI redesign Stage 3

1. **Reuse the public read contract.** Keep existing projections, visibility gate, RLS/media delivery and exact money formatter. Present only asking price and truthful bidding unavailability; seller category/verification and auction status cannot be invented from missing data. No schema, dependency or transaction feature is needed.
2. **A focused gallery interaction island.** Use responsive contain-fit photos, small lazy thumbnails, deliberate horizontal touch gestures and a viewport-filling native dialog. Mount only the selected viewer image. Explicit Tab/Shift+Tab cycling supplements modal isolation; Escape, focus return and scroll restoration are browser-tested. No decorative carousel animation or browser-fullscreen permission is required.
3. **Disclose condition before detail.** Known defects and seller-declared accident/flood history precede essential specifications on phones. Longer description follows specifications; display approval and independent inspection guidance remain separate. Null fields are unconfirmed, never inferred.
4. **Safe return navigation and incremental related reads.** Carry canonical catalog context through an optional `from`, validate with the bounded catalog schema and accept only `/vehicles`. Reuse the existing five-row related query, exclude the current listing and show at most four shared cards behind local Suspense. Empty/error sections are omitted.
5. **Evidence before handoff.** Isolated actual PostgreSQL/RLS fixtures and headless Chrome cover five widths, transport failures, image states, keyboard/touch and selected-image request budgets. Wait for related content for settled screenshots; capture deliberate loading separately. Provider/Auth/Storage/SMTP and full screen-reader/translation acceptance remain pending. See docs/design/stage-3-2026-10-11/implementation.md.

## 2026-10-11 — UI redesign Stage 4

1. **Retain email/password and security contracts.** No verified social/SMS setup exists. Preserve clients, Proxy refresh, independent confirmed-user guards, trusted callback origins, PKCE/token-hash verification, RLS and current admin grants. No cosmetic migration or Auth configuration change.
2. **Defer optional profile entry.** Signup collects only email/password; send the existing empty optional name rather than remove or duplicate its service contract. Keep 12–128-character passwords and the existing recovery confirmation field. Existing legal links remain; no new required agreement is invented.
3. **Shared validation and focused controls.** Use existing Button/Input plus PasswordField, shared Zod schemas and one allowlisted FormData mapper. Show specific inline errors and first-invalid focus, reset secrets after server responses, retain non-secret profile values and guard duplicate Auth submissions synchronously.
4. **Truthful email instructions and resend.** Only service success reveals the notice, not verified status. Generic signup/recovery responses avoid account enumeration. Real SDK resend is signup-only; recovery repeats the established reset operation. Calculate the UI cooldown from a deadline to tolerate delayed timers. Provider rate limits remain authoritative.
5. **Safe navigation, restrained account.** Retain only established account/password/admin return paths across auth screens and redirect validated customers past unnecessary forms. Keep neutral My account public navigation without session lookup/polling. AccountView displays own permitted fields, actual confirmed email and grant-dependent admin entry; optional dealer details remain expandable and separate.
6. **Separate UI transport evidence from provider acceptance.** New isolated Auth/profile fixture drives real SDK/actions and rendered UI using synthetic responses; public SQL/RLS checks remain real. No GoTrue/signing/SMTP claim. CLI is unavailable and Docker daemon is stopped, so actual disposable-provider acceptance remains pending. See docs/design/stage-4-2026-10-11/implementation.md.

## 2026-10-10 — Selected Phase 2 visual redesign

1. **Refine the existing application.** The user selected the first displayed concept, Premium Automotive Minimalism. Keep thin routes, feature components, public-safe query services, exact money formatting, RLS and Auth contracts; introduce no new project, dependency or business workflow.
2. **Semantic light-mode tokens and local typography.** Warm white, white surfaces, charcoal, green and sparse non-text gold replace the prior lime identity. Use separate structural and interactive-control borders so form boundaries exceed 3:1 contrast against adjacent base surfaces. Bundle a 69,760-byte Geist variable WOFF2 from official revision 10dc7658f13c38a474cde201bb09a4617267545b with its SIL OFL 1.1 license; use [Next.js local fonts](https://nextjs.org/docs/app/getting-started/fonts). Existing script fallbacks remain; no untranslated locale becomes selectable.
3. **Illustration is distinct from listings.** A separately generated 226 KiB WebP depicts a compact car and is visibly labelled Illustrative image — not a listing. The exact static asset path is allowlisted for Next Image. It does not stand in for an approved vehicle photo and does not change the Storage/RLS boundary.
4. **Clarify current capability.** Search is the homepage's primary task. Unsupported category tiles become a short availability note. Prices remain seller asking prices. Filters/sorting use their existing GET submissions; model/year remain disclosed on demand. Selling navigation states coming soon; the five planned stages are a static informational list. Bidding remains a truthful unavailable notice.
5. **Rendered verification precedes handoff.** Compare the selected raster and actual screenshot at normalized density, correct substantial spacing differences, then review mobile/tablet/desktop and populated isolated fixtures. Record expected adaptations (clean photo edges, restrained heading size, readable captions/full footer) rather than claim pixel identity or full multilingual/provider acceptance.

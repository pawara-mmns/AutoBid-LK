# UI redesign Stage 4 — authentication and account

2026-10-11, Asia/Colombo. Authorized scope: sign in, sign up, confirmation/recovery instructions, password update and existing basic account UI, within development Phase 2. Implementation, final browser verification and rendered QA complete. Stopped after Stage 4. No development Phase 3 or UI Stage 5 work is authorized.

## Starting point and improvements

Read AGENTS, README, phase log, roadmap, architecture, decisions and database boundaries. Git began clean; UI Stages 1–3 were present. Inspected existing forms, Server Actions, Supabase clients/proxy, callbacks, guards, private profiles, grants, dictionaries and tests. Captured the original sign-in/signup/recovery/account screens at 360/1440px before editing production source.

The approved warm-white/charcoal/green palette, local Geist/script fonts, shared shell, Button and Input remain. Auth pages use a quiet centered form with readable labels, one primary submission and clear secondary navigation. No illustration, gradient panel, social/SMS button, invented activity or second design system.

- Registration now asks for email and password only. Optional display-name entry is deferred to the existing profile form; the existing validated signup contract still receives an empty optional name. Password requirements remain 12–128 characters with intentional spaces preserved. No new confirmation requirement, legal checkbox, buyer/seller split or privileged metadata is introduced. Existing legal links remain in the footer.
- A focused PasswordField offers keyboard-accessible show/hide controls with meaningful labels, retained values, autocomplete, 48px targets and visible focus. Autocapitalization/autocorrection/spellcheck stay off even when a password is visible. The same field supports current/new/repeated passwords. Passwords are uncontrolled and reset after server responses; they never enter returned form state or logs.
- Client validation uses the same Zod schemas and allowlisted form-input mapping as Server Actions. Invalid fields receive specific inline guidance, aria-invalid/describedby and first-invalid-field focus. Server validation remains authoritative. Pending fieldsets/buttons and a synchronous submission guard prevent accidental repeated Auth submissions.
- Signup/recovery success renders entered-email instructions with inbox/spam guidance and a change-email path. Registration wording handles new/existing accounts without claiming confirmation. Recovery wording does not disclose account existence. Confirmation resend calls the real SDK signup-resend operation; recovery sends a new reset request. A 60-second UI cooldown supplements provider throttling; it is not a server abuse-control boundary and can be bypassed by reload. Provider 429 responses remain friendly.
- Validated, confirmed, non-anonymous customers opening auth pages return to an allowlisted destination. Invalid-link feedback remains visible. `/account`, `/account/password` and `/admin` are the established permitted return paths; cross-screen links retain them and reject external/ambiguous values. No new redirect class or provider configuration. Signup confirmation still uses its established default account callback; a safe next destination remains available through the notice's sign-in link. Recovery always keeps its established password-update callback.
- The account route remains thin and independently guarded. AccountView separates profile details from account access, displays confirmed email only after the existing guard and keeps browse/password/logout destinations real. Non-secret name/business edits persist through errors. Optional dealer details are a native expandable section, with existing pending/verified/rejected semantics and unchanged service. Admin entry appears only for a current database grant. No bids/vehicles/dashboard placeholders or private documents are added.
- The header keeps its neutral My account entry: guests reach the existing protected-route sign-in redirect and validated customers reach their account. No public cookie lookup, client session polling or claim that a visitor is signed in is added to public browsing.

## Authentication and security boundaries

Email/password is the only supported method found. Local config requires email confirmation; no social/SMS provider configuration is present in the checked-in config. Hosted provider settings were not inferred from public keys or changed. Phone OTP/social sign-in remain unavailable future enhancements and are omitted.

Existing browser/server clients, cookie adapters, Proxy getClaims refresh, independently validated getUser guards, private/no-store and no-referrer headers, fixed callback origins, PKCE/token-hash verification, ownership derivation and least-privilege SQL/RLS remain. No getSession authorization, elevated key, admin self-assignment, schema/migration, SMTP setting, dependency or environment-file change. Existing profile/dealer services and public marketplace source are preserved.

Reviewed official [Supabase SSR clients](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [confirmation resend](https://supabase.com/docs/reference/javascript/auth-resend), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits) and [React form actions](https://react.dev/reference/react-dom/components/form). Supabase remains responsible for server-side throttling. Production delivery/rate-limit/abuse configuration still requires its existing acceptance gate.
